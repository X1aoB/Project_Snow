# Public immersive deployment

The public process exposes only `/public/v1` and the static immersive client. The existing internal `/api/v1`, attachments, voice, agents and workspace are not mounted by `public_main.py`.

The 0.9.6 client uses IndexedDB v4: messages and conversation metadata are stored separately, the first 60 messages are loaded eagerly and older history is paged in 40-message batches. Deterministic `displayBlocks` and optional whitelisted `stageMotion` metadata are stored with assistant messages. Stage motion is presented only for the live response and is never replayed by history rendering, character switching or reload. Drafts, pins, recent characters and sticker favourites remain browser-local. If IndexedDB is unavailable, the client falls back to a non-persistent in-memory session instead of blocking chat.

One signed `public-state-2` world package is maintained per anonymous subject. A v1 package is accepted, completed with the current 22-character presence registry and re-signed as v2. Version 0.9.6 keeps the 0.9.5 state, key-rotation and rollback compatibility. Text messages may contain one manifest-backed sticker after the message text; in-person messages continue to accept `speech` and `action`. A top-level `stage_motion` response field is presentation-only, defaults to `none`, and is forced to `none` for text communication or invalid values. Public presence endpoints are:

- `POST /public/v1/presence/resolve`: read a character scene without changing revision.
- `POST /public/v1/presence/transition`: move to the character or open the communicator without a model call.
- `POST /public/v1/presence/arrival`: make one idempotent 50/50 arrival decision; only the noticed branch consumes chat quota and invokes the current BYOK model.

The client commits `/presence/transition` before requesting `/presence/arrival`. Arrival generation is best-effort: an empty response, queue limit or provider failure keeps the signed location transition, restores the in-person composer and returns no fabricated role dialogue. Public immersive calls send the provider-specific disabled-thinking fields for DeepSeek and DashScope while retaining the two-call budget. In text communication, a validated controlled-location invitation that the character clearly accepts moves only that character and records that she is waiting; the analyst moves only after choosing “go to her”. In-person acceptance retains immediate joint movement. The public catalogue contains 15 selectable destinations, including the active character's room and the analyst's room; the legacy canteen remains readable but is not selectable for new invitations. A failed scene update never discards valid dialogue.

The daily character schedule is deterministic (HMAC-derived) from the anonymous subject and Hong Kong calendar date, so different visitors do not share a schedule. The first state request after Hong Kong midnight lazily refreshes location, activity, analyst position, pending rendezvous and recent state events while preserving conversations and relationships. State consumers compare `(schedule_date, schedule_revision)` and reject a late package from an older date.

BYOK API keys are sealed into a fixed, absolute 12-hour AES-GCM envelope bound to the anonymous subject. There is no sliding renewal and no migration or extension of an already-issued two-hour envelope. The browser stores the envelope only in the current tab's `sessionStorage`, so closing the tab clears the local copy before its server-verifiable expiry. Provider calls still receive the current user content and key according to the selected provider's privacy policy.

Sticker media `2026.08.19.sticker.1` is a separate independently verified public package with 363 source resources, chat-sized display derivatives and thumbnails. It records role/emotion metadata, per-file fixed revisions, uploader and hashes, CC BY-NC-SA 4.0 attribution evidence, and manifest/SHA256SUMS verification before promotion. Avatar media `2026.08.19.avatar.1` and data `2026.08.19.1` have the same fail-closed provenance rule. None of these Wiki-derived packages is copied into the GPL application image.

Version 0.9.6 reuses without modification the 18 content-hashed, lossless WebP Mia face crops and matching 620×1024 transparent full-body stage derivatives introduced in 0.9.5. Their public manifest records the selected review variant, source and derivative hashes, deterministic transforms, and the operator's explicit 2026-09-02 instruction to waive independent rights verification for this publication. The waiver is not represented as ownership or license verification, applies only to these 18 approved source selections, and is disclosed on the public privacy/materials page with the takedown contact. All other character portraits continue to use the independently verified avatar package.

## Candidate and public-access gate

Preserve the currently configured Cloudflare Access policy throughout inactive-colour staging, candidate acceptance and promotion; the 0.9.6 release must not add, remove or alter an Access policy. Do not add or modify a MyWebsite play button. Test the candidate through the private SSH tunnel, then exercise the public site using the access state already in force. A security or abuse anomaly restores Access first; an application failure rolls back the exact prior colour and release pins. Do not modify or reload SSH configuration, and verify a fresh root key session immediately before and after traffic promotion.

`PUBLIC_ENABLED_PROVIDERS` starts empty; add a provider ID only after a real-key smoke test for that provider succeeds. Every user action is capped at two provider HTTP calls. Compatibility probes and uncertain-timeout retries are disabled so a browser recovery can reuse the original request ID and server idempotency result without duplicate billing.

## Server layout

- `/srv/project-snow/repo`: root-owned mode-`0700` Git checkout of the full Project Snow repository. Git hooks are disabled. Only the root-owned release runner fetches or checks out commits.
- `/srv/project-snow/app`: symlink to `/srv/project-snow/repo/App`, so operations always run from the selected repository commit's application tree.
- `/srv/project-snow/inbox`: the deploy account's only writable release path, mode `0700`. It accepts fixed-name `release-<40-character-sha>.json`, `data-<version>.tar`, `avatar-<version>.tar` and `sticker-<version>.tar` inputs. The root runner opens inputs without following symlinks and rejects unexpected ownership, links, size, member types or paths. The CI release manifest is regenerated from the trusted checkout and fixes each package's manifest digest (plus avatar/sticker `SHA256SUMS` digest), so a deploy credential cannot substitute different content under an approved version.
- `/srv/project-snow/data/releases/<version>`: immutable verified data releases. Every colour environment records `PUBLIC_DATA_ROOT` as one exact release directory; `DATA_ROOT` and `APP_RUNTIME` are derived from that value and never use a mutable symlink in an API container.
- `/srv/project-snow/data/current` and `/srv/project-snow/data/previous`: legacy/manual compatibility links only. Blue/green serving and rollback do not resolve these links.
- `/srv/project-snow/runtime`: read-only serving runtime and release metadata.
- `/srv/project-snow/runtime/public-<main-sha>.env`: versioned non-secret public settings generated from the release manifest for a staged colour; the promoted colour keeps this path in its colour compose environment.
- `/etc/project-snow/public.env`: root-owned non-secret production settings, mode `0600`; the root runner supplies it to Compose without exposing it to the SSH account.
- `/etc/project-snow/images.env`: root-owned fixed infrastructure image digests, mode `0600`.
- `/srv/project-snow/runtime/compose.env`: the last promoted application, embedding and infrastructure image set, written atomically by `ops/promote.sh`.
- `/srv/project-snow/runtime/colours/{blue,green}.compose.env`: the last staged environment for each colour; the inactive colour can be inspected and rolled back without overwriting the active colour's metadata.
- `/srv/project-snow/runtime/origin-edge/<environment-sha256>.compose.env`: root-owned mode-`0600` content-addressed copies of the exact environment used by the independently live direct-origin listener. These copies are not colour staging slots and must survive later restaging of either colour.
- `/srv/project-snow/releases/colours/`: per-colour release markers and manifests. `/srv/project-snow/releases/active-colour` must already exist, be readable and contain exactly `blue` or `green`; deployment stages only the other colour, and promotion rejects the colour already named active.
- `/srv/project-snow/releases/configurations/<main-sha>`: immutable runtime-configuration snapshots containing Compose, the internal and origin-edge Caddy configurations, the two public origin trust certificates, the bounded TLS installer, the Cloudflare-origin firewall helper and systemd units, Squid, Neo4j, PostgreSQL and locked-image build inputs. Each colour has a `*-config.json` binding that fixes the colour, commit, snapshot path and every file hash. Candidate operations use the candidate snapshot rather than the mutable checkout. A pre-direct-origin binding has the original seven files, the one migration-era fixed-mount direct-origin bundle has the exact original four direct-origin additions (eleven total), and a current immutable-TLS direct-origin binding has all fourteen files. Mixed or partial bundles are rejected. On the first 0.9.0 deployment, the active rollback snapshot is reconstructed with `git archive` from the SHA already recorded in its marker and is rejected if any file differs.
- `/srv/project-snow/releases/current-config.json`: the binding for the last promoted application colour and its recreated edge/runtime services. It is updated only after the new edge and mailer have passed their post-switch gates; rollback continues to use the target colour's own binding. During the dual-path migration it is not a complete live-ingress inventory: an `origin-edge` retained across a legacy application rollback may still mount its newer immutable snapshot.
- `/srv/project-snow/releases/live-origin-edge-config.json`: the root-owned mode-`0600` durable live-ingress binding. It copies the exact immutable configuration hashes and binds them to one content-addressed origin-edge environment. Promotion validates this pointer before any traffic mutation, publishes it with file and parent-directory fsync after a listener is proven running, and uses it as the recovery source even after both colour staging slots have moved on. A controlled rotation keeps a separate root-only recovery copy until either the new listener commits or the old listener is fully restored.
- `/srv/project-snow/media/current`: the atomically promoted, independently verified avatar media package. It is mounted read-only into both API colours.
- `/srv/project-snow/media/releases/<version>`: immutable, independently verified media releases. A staged API colour pins `PUBLIC_MEDIA_ROOT` to its release directory so a new package cannot invalidate the active or rollback colour during acceptance.
- `/srv/project-snow/media/stickers/current`: the legacy fallback sticker package. New colours pin an immutable release directory instead, so staging a candidate cannot invalidate the active or rollback colour.
- `/srv/project-snow/media/stickers/releases/<version>`: independently verified sticker releases. `ops/fetch-promote-sticker-media.sh <version> stage-only` verifies 363 resources and 363 thumbnails without changing the legacy `current` symlink.
- `/etc/project-snow/secrets`: root-only secret files, mode `0700`; individual files mode `0600`. The public image starts with a minimal root entrypoint, copies only its approved secret files into a private container tmpfs with mode `0400`, and immediately drops to the unprivileged `snow` user before Alembic, Uvicorn or admin code runs. Secret values are never placed in Compose environment interpolation.
- `/etc/project-snow/feedback-mailer.env`: root-owned mode `0600` non-secret mailer settings. It must contain exactly `PUBLIC_FEEDBACK_EMAIL_TO`, `PUBLIC_FEEDBACK_EMAIL_FROM`, `PUBLIC_FEEDBACK_SMTP_HOST`, `PUBLIC_FEEDBACK_SMTP_PORT` and `PUBLIC_FEEDBACK_SMTP_USERNAME`; database and SMTP passwords remain separate root-only mounted files. Sender, host and username may all be empty to disable receipt email, but partial SMTP configuration is rejected. Deploy and promote reject extra keys, duplicate keys, malformed values, a symlink or unsafe ownership/mode.
- `/etc/project-snow/cloudflared`: root-only named-tunnel configuration and credentials. Ingress maps only `snow.xiaob.dev` to `http://caddy:8080`, followed by an explicit `http_status:404` catch-all.
- `/etc/project-snow/origin-edge`: root-owned mode-`0700` TLS material. Each public certificate pair has an immutable `releases/<bundle-sha256>` directory containing `origin-cert.pem`, `origin-key.pem`, `aop-ca.pem` and exact install metadata as root-owned, single regular files with mode `0400`. The public Origin CA certificate and public AOP trust CA are fixed by Git and the CI manifest. The sole private origin key is never stored in Git or a release archive: `deploy.ps1` uploads it to one SHA-named file inside the deploy-owned mode-`0700` inbox, and the root runner requires exact SHA-256, owner/group, mode `0600`, size, link-count and `O_NOFOLLOW` checks before OpenSSL proves it matches the Git-bound certificate. The verified bundle is installed by same-filesystem atomic rename and the inbox copy is removed. Existing bundles are never replaced, so a failed stage cannot damage live TLS material.
- The application Caddy port `8080` exists only on internal Docker networks and is not published on the host. `cloudflared` reaches it through the existing `edge-client` network. A separate least-privilege Caddy sidecar terminates origin TLS on container port `8443` and reaches only `caddy:8080` through the dedicated internal `origin-backend` network; the sidecar is not attached to the shared `edge-client` network.
- Public API colours publish no host ports. A successful stage resolves and validates the candidate container's address on the internal `app` bridge; private acceptance forwards a client-local `127.0.0.1` socket to that address through authenticated SSH. There is no candidate listener in the server host namespace, firewall or Cloudflare Tunnel.
- `127.0.0.1:19090` remains the intended feedback-administration endpoint through an SSH tunnel. This separate legacy path still depends on Docker instantiating a loopback publication for a container whose `data` and `management` networks are internal. On hosts where Moby leaves that runtime mapping empty, the admin endpoint is unavailable; do not attach admin to an uplink network as a workaround. A future control-plane change should use the same root-validated internal-address SSH pattern before operators rely on this endpoint.

The production image runs `fingerprint_public_frontend.py` after copying the client. It creates 16-hex-character SHA-256 filenames for every immersive scene SVG, rewrites the image copy of `app.js` to a fixed scene URL map, then fingerprints `app.js`, `app.css`, `privacy.js` and the shared immersive stylesheet and rewrites only the image's HTML references. HTML and the original development URLs remain `no-store`; fingerprinted files use `public, max-age=31536000, immutable`. The checked-in HTML and JavaScript retain release-specific cache query strings and canonical scene paths for direct local development.

## Direct-origin Phase A

Phase A keeps the existing named Tunnel and adds an independently secured direct-origin path. `origin-edge` uses the same digest-pinned Caddy image, publishes host `443/tcp` to container `8443`, disables automatic HTTPS and HTTP/3, accepts only HTTP/1.1 and HTTP/2, and requires a verified Cloudflare client certificate before proxying to the internal Caddy. Its TLS listener is not SNI-scoped, so every TLS handshake uses the single mandatory client-authentication policy; the HTTP layer separately accepts only `Host: snow.xiaob.dev` and returns 421 for every other host. It does not publish port 80 or any UDP port. The main Caddy remains attached only to internal networks and is never placed directly on an uplink.

Before an operator changes DNS, provision a Cloudflare Origin CA certificate for `snow.xiaob.dev`, commit only its public certificate and the public Authenticated Origin Pulls trust CA under `config/origin-edge`, and supply the matching local private key through `deploy.ps1 -OriginPrivateKeyPath`. Set SSL/TLS encryption to Full (strict), enable per-hostname Authenticated Origin Pulls for only `snow.xiaob.dev`, and keep the DNS record orange-cloud proxied. Authenticated Origin Pulls applies only to the direct listener; the retained Tunnel continues to authenticate with its connector credentials. These Cloudflare control-plane changes are deliberate external prerequisites: release scripts neither perform nor infer them. Do not change the DNS/Tunnel route until the direct path has passed its host-side gates and both blue and green retained snapshots are direct-origin capable.

At the VPS provider, expose only TCP 443 for the origin path. Keep TCP 80 and UDP 443 closed; there is no public HTTP redirect listener and no QUIC origin listener. The provider may allow TCP 443 from all sources when it cannot express Cloudflare ranges, but the host must remain fail closed:

- UFW stays active with `IPV6=yes`, default deny for incoming and routed traffic, and no blanket `ufw allow 443` rule.
- `/usr/local/sbin/project-snow-origin-firewall` obtains IPv4 and IPv6 ranges from both Cloudflare plaintext endpoints and its API, requires the three results to agree, validates public canonical CIDRs, and commits a root-owned last-known-good state only after checked nftables and UFW transitions succeed.
- An independent nftables `inet` table covers both host INPUT and Docker FORWARD, so Docker's published-port DNAT cannot bypass the allowlist. Only Cloudflare source ranges may start original-direction TCP 443 flows; all original-direction UDP 443 flows are dropped.
- `origin-uplink` has the fixed Linux bridge name `ps-origin0`. After admitting only reply-direction `ESTABLISHED,RELATED` traffic for Cloudflare-originated connections, nftables drops every other packet from that bridge to the host and every other forwarded packet regardless of destination interface. The dedicated internal `origin-backend` has the fixed Linux bridge name `ps-origin1`; nftables likewise admits only reply-direction established traffic from that bridge to the host and drops every other host-input packet. It deliberately does not drop same-bridge forwarding, so `origin-edge` can reach Caddy while neither dedicated bridge provides a host-gateway escape. The TLS sidecar therefore cannot initiate arbitrary Internet, host-gateway or cross-bridge connections while it holds the origin private key.
- Docker Engine must report a stable numeric server version at or above `26.0.0`, which includes the Moby fix for [GHSA-mq39-4gv4-mvpx](https://github.com/moby/moby/security/advisories/GHSA-mq39-4gv4-mvpx). Both the sidecar and its probe pin their upstream DNS to container loopback (`127.0.0.1`), so Docker's embedded resolver retains internal service discovery but cannot forward external queries through a host-loopback resolver. Before the first key-bearing sidecar start, the already running candidate API's immutable image ID is reused for a separate Python-standard-library probe with no environment, mounts or secrets and with a read-only root, all capabilities dropped and `no-new-privileges`. External name resolution, direct TCP to `1.1.1.1:80/53`, a direct UDP DNS query, both dedicated bridge host gateways and the known application-bridge API must all be unreachable, while `caddy` resolution and HTTP health across `origin-backend` must succeed. The probe is removed and the network/container state is revalidated before the real sidecar may start.
- The official Caddy Linux image marks `/usr/bin/caddy` with the `CAP_NET_BIND_SERVICE` file capability. Dropping that capability from the bounding set makes Linux reject `execve` even when Caddy listens only on unprivileged container port `8443` ([caddy-docker #396](https://github.com/caddyserver/caddy-docker/issues/396)). The sidecar therefore drops `ALL` capabilities and adds back exactly `NET_BIND_SERVICE`; the runtime gate rejects any additional capability, entrypoint, command, mount or network. The same immutable image and TLS mounts must also pass a one-shot Caddy validation before the production sidecar starts.
- The enabled oneshot is `RequiredBy=` and ordered `Before=docker.service`; its daily timer refreshes ranges. A missing nftables binary, inactive/unsafe UFW, disagreement between range sources, invalid state or failed restore prevents a new `origin-edge` from starting. Never work around this by flushing rules or opening 443 globally.

On an already prepared VPS, direct-origin staging does not run `prepare_debian.sh` and does not modify SSH configuration. It installs the immutable helper and units only after candidate application checks pass, performs one successful manual `update`, and enables the boot dependency and timer. At the first direct-origin promotion, when no production `origin-edge` is running, the target immutable Compose snapshot force-creates it without starting it. The gate requires exactly one stopped container, only `ps-origin1` plus `ps-origin0`, exactly `dns: ["127.0.0.1"]`, the exact digest-pinned Caddy image and command, the exact snapshot Caddyfile plus three read-only TLS mounts, and only host TCP 443 mapped to container TCP 8443. It independently inspects both Docker networks and actual Linux links, requiring driver `bridge`, `EnableIPv6=false`, the exact bridge-name option and exact Compose project/network labels; `ps-origin0` must be non-internal and `ps-origin1` must be internal. The uplink may contain no endpoint other than this exact sidecar, and the backend may contain only that sidecar and the exact running Caddy. Existing same-name networks with different metadata, endpoint membership or link type fail closed and are never deleted or repaired automatically. The firewall update/restore must then succeed before the no-secret isolation probe runs; the probe must increment all three comment-identified nftables drop-rule counters, is removed, and the stopped container/network state is revalidated. Only then are the other edge services recreated and that same inspected container started. The running gate rechecks Docker's effective DNS and port publication, exact image, command, mounts, endpoints and network/hardening state, then validates the mounted outer Caddy configuration inside the container. A running listener whose complete live binding already matches the target is retained without stop, recreate or start. For a forward promotion from the migration-era fixed mounts or immutable bundle A to bundle B, replacement is permitted only when the running listener exactly matches its durable live binding and the separately authenticated Tunnel container is still running with its exact mounts and networks. Before removing the old listener, promotion content-addresses its environment, durably publishes its live binding and saves a root-only recovery copy. The Tunnel is not recreated during this window: the old listener is stopped and removed, the target is created stopped, then material, network, firewall and no-secret isolation gates run before start. Any failure recreates and validates the exact old listener, restores the last-known-good firewall and live binding, and keeps the Tunnel; an unrecognized listener is never adopted. Application rollback does not rotate the TLS bundle backward and instead retains the independently live listener as an overlay while moving only its Caddy backend. `prepare_debian.sh` merely records the `nftables` package and private certificate directory for fresh-host provisioning; if an existing host lacks that prerequisite, resolve it through the provider's root recovery workflow instead of rerunning the SSH-hardening migration.

Application promotion and application rollback are not edge-route migrations. Service discovery is restricted to the fixed `caddy`, `origin-edge`, `cloudflared` and `egress-proxy` names, so a legacy snapshot is never passed an unknown `origin-edge` service. Rolling an application back to a legacy colour recreates that colour's Caddy and Tunnel service but deliberately leaves the already running `origin-edge` untouched; the switch attaches the recreated legacy Caddy to the retained `ps-origin1` network with the `caddy` alias, so direct origin continues to reach the restored application if DNS still points through the orange-cloud A/AAAA route. Likewise, an application transition never retires cloudflared merely because both colours understand direct origin. Stopping either ingress requires a separate, explicitly authorized edge rollback/migration after external confirmation of the active Cloudflare DNS or Tunnel route. The only automatic exception is fail-closed safety: if the origin firewall cannot be restored, `origin-edge` is stopped and public 443 remains closed while cloudflared can continue serving. `live-origin-edge-config.json`—not `current-config.json` and not either mutable colour slot—is the retained ingress inventory. Configuration garbage collection must keep its configuration root and content-addressed environment, plus any explicitly preserved `live-origin-edge-config.json.restore.*` recovery copy after a critical restoration failure; do not delete them merely because both colour bindings now point elsewhere.

Direct-origin acceptance must prove all of the following before the Tunnel is retired: the Cloudflare hostname succeeds with a valid edge request; a direct connection from a non-Cloudflare source to the VPS 443 fails; Origin CA hostname verification and Authenticated Origin Pulls succeed; TCP 80 and UDP 443 remain unreachable; the sidecar cannot resolve external names or initiate Internet, host-gateway or cross-bridge connections through either `ps-origin0` or `ps-origin1`; and the allowlist still applies after Docker restart, UFW reload and host reboot. Retain the Tunnel until both colour snapshots and the retained rollback target have passed these checks.

## One-time least-privilege migration

Older installations made `deploy` a member of the root-equivalent Docker group. Preserve the currently configured Cloudflare Access state while changing that boundary. Select the exact CI-passing 0.9.2 main SHA; do not use an uncommitted checkout or a branch name.

From the trusted local workspace, use the one-time migration client with the CI release manifest for the same SHA. It creates a Git archive containing only the seven host-preparation files from that exact `origin/main` object and fixes its SHA-256. A host-bootstrap program read from the same Git object is streamed into the digest-pinned CI application image; it opens the uploaded archive without following links, verifies the digest and exact member set, then schedules a host systemd oneshot. The helper container exits before the host unit restarts Docker. The host unit runs the firewall, fail2ban, SSH and Docker preparation and passes the exact SHA into the root-runner bootstrap. Nothing from the old deploy-owned server checkout is executed as root. This is the final authorized use of the deploy account's Docker access:

```powershell
& App/scripts/bootstrap-release-runner.ps1 `
  -Sha <exact-0.9.2-main-sha> `
  -ManifestPath <downloaded-CI-release-manifest.json> `
  -SshConfig App/runtime/project-snow-ssh-config
```

The root bootstrap clones the fixed HTTPS origin into a new directory with hooks disabled, verifies the requested SHA is on `origin/main`, installs the runner and validated sudoers file, atomically replaces the historical checkout, makes runtime/release/data/media roots root-owned, creates the deploy-owned mode-0700 inbox, changes all three environment files to root-owned mode `0600`, and removes every supplementary group from `deploy`, including `docker`. The client waits for the host systemd unit, then opens a fresh connection and requires active UFW/fail2ban, no Docker group or socket access, runner-only sudo and the exact controller SHA. If the transitional Docker call is unavailable, use the hosting provider's root console to run `prepare_debian.sh --controller-sha <sha>` from a fresh exact-SHA clone, never from the historical checkout:

```sh
/path/to/fresh-exact-sha/App/ops/prepare_debian.sh \
  --controller-sha <exact-0.9.2-main-sha>
```

The previous checkout is retained under `/srv/project-snow/backups/repo-before-root-runner-<UTC timestamp>` with mode `0700`; the script does not stop or recreate running production containers. Existing SSH processes retain their old supplementary group list, so disconnect every deploy session after the script succeeds. Open a fresh connection and require all of these checks before staging or removing Access:

```sh
id -nG | tr ' ' '\n' | grep -Fx docker && exit 1 || true
docker info >/dev/null 2>&1 && exit 1 || true
sudo -n /usr/local/sbin/project-snow-release status
sudo -n /bin/sh -c true >/dev/null 2>&1 && exit 1 || true
```

`status` must report `deploy_has_docker_group: false`, `deploy_can_access_docker: false`, `deploy_process_has_docker_socket_group: false`, `ufw_active: true`, `fail2ban_active: true`, `sshd_hardened: true` and `host_safety_preflight: true`; after the bounded upgrade, `release_runner_sha256` must equal the exact target manifest hash. Its installed release arrays contain only packages that match the digest index in the trusted controller checkout and pass a complete package verification. If any check fails, keep Access enabled and return through the root recovery channel; never add `deploy` back to the Docker group as a workaround. Fresh Debian provisioning runs the same bootstrap from `prepare_debian.sh`. Populate and validate the dedicated `/etc/project-snow/feedback-mailer.env` from `ops/feedback-mailer.env.example`; do not put SMTP settings back into `public.env`.

The production SSH baseline deliberately retains direct root recovery by public key while keeping routine releases on the constrained `deploy` account. It requires `PermitRootLogin prohibit-password`, disables password and keyboard-interactive authentication, disables X11 forwarding, limits sessions, and fixes `AllowUsers` to exactly `deploy root`. The root `authorized_keys` file must be a non-empty, single-link, root-owned regular file with no group or other write permission. `sshd -T` reports the canonical value as `permitrootlogin without-password`; the runner verifies that value for both root and deploy contexts before every mutation. This preserves administrator recovery without allowing a root password login, but the root private key remains a full-host credential and must be protected accordingly.

The already installed c479 runner can perform one bounded self-upgrade during the first exact direct-origin `stage`; no root console, SSH configuration change or broader sudo rule is used. The old runner first fetches the pinned HTTPS origin, requires the requested commit on `origin/main`, regenerates and compares the complete target release manifest, verifies both image digests, and invokes only that target commit's `deploy.sh`. The manifest separately pins the target runner and the unchanged sudoers source. Before any durable staging write, target `deploy.sh` requires the installed runner to be either the exact c479 compatibility blob or the exact predecessor blob declared by a newer runner, compares the installed root-owned mode-`0440` sudoers file byte-for-byte with its target source, validates it with `visudo`, and refuses to continue if any deploy-owned process still carries the Docker socket group. The sudoers file is never rewritten by `stage`.

After candidate and first firewall gates pass, target `deploy.sh` extracts the runner from the exact Git blob into a same-directory root-owned temporary file, checks shell syntax, Git object identity, SHA-256, ownership, mode and link count, fsyncs it, preserves an exact same-filesystem rollback copy, and replaces `/usr/local/sbin/project-snow-release` with one atomic rename. The old executing shell continues on its already opened inode; a fresh `status` process must then report the target controller and runner hashes plus a fully active server-side mutating preflight. A normal later failure atomically restores the previous runner before the old controller restores its checkout. An abrupt power loss or `SIGKILL` can leave either complete trusted inode, never a partial script; repeat the exact stage after checking `status`. Future runners pass their exact predecessor controller and runner hashes through a cleared, runner-owned environment, so the same bounded upgrade path does not broaden the deploy account's command surface.

Run Alembic before starting a new application colour. Never let the web process auto-create production schema. Application migrations follow expand/contract compatibility with the previous application image.

The routine SSH `deploy` account is deliberately not in the `docker` group and cannot read the repository, production environments or release metadata. Direct root public-key SSH is retained as the separately controlled administrative recovery path; routine releases still use `deploy`. Its only privileged command is the root-owned `/usr/local/sbin/project-snow-release` runner through a single unchanged sudoers rule. The runner accepts only `stage`, `promote`, `rollback` and `status`, validates exact argument counts, clears the caller environment and uses a fixed HTTPS origin. Every mutating operation repeats the effective daemon policy, safe root authorized-key metadata, active UFW, active fail2ban `sshd` jail, absence of `deploy` from the Docker group, inability of `deploy` to query the Docker daemon, and absence of the Docker socket group from every still-running deploy-owned process; a generic failure aborts before the release lock, fetch, filesystem write or privileged Docker work. `status` remains a read-only diagnostic and does not create the release lock. Successful mutating operations then serialize with `flock`. For staging the runner fetches `origin/main` as root, refuses a SHA that is not an ancestor, checks out a clean detached commit with hooks and fsmonitor disabled, regenerates the complete release manifest, and verifies that the application and embedding tag digests belong to that SHA before entering `App/ops/deploy.sh`. HUP, INT, QUIT, TERM and PIPE are forwarded to the exact request child and waited: a non-durable stage restores its runner-bound predecessor controller and returns `128+signal`, while only the exact fsynced nonce receipt can acknowledge success. Promote and rollback use the same request-bound child rule; a signal after traffic mutation makes `promote.sh` finish previous-runtime recovery, and the parent acknowledges success only after the atomically published current environment, manifest, config and marker pass its own exact durable-state check. Promote and rollback otherwise require the exact staged SHA and run through the last successfully staged trusted controller. This prevents a caller from obtaining a root shell through Docker, staging an unmerged commit, bypassing the host baseline or substituting deployment scripts. A direct-origin release manifest pins SHA-256 values for all fourteen runtime/build inputs plus the runner and unchanged sudoers source: Compose, both Caddy configurations, the two public origin certificates, bounded TLS installer, origin-firewall helper and two units, Squid, the Neo4j entrypoint, PostgreSQL configuration, the public Dockerfile, the hashed Python requirements lock, and the two release-control files. Legacy seven-file and exact migration-era eleven-file snapshots remain readable for rollback, while any mixed or partial direct-origin bundle is rejected.

Pin PostgreSQL, Qdrant, Neo4j, Caddy, cloudflared and Squid by digest in `/etc/project-snow/images.env`; `origin-edge` deliberately reuses the Caddy digest. The local deployment command requires the CI manifest generated by the selected, passing `main` SHA and the matching local origin key through `-OriginPrivateKeyPath`. `App/scripts/deploy.ps1` first queries the root runner; a package is treated as installed only after the runner matches it to the trusted artifact digest index and completes all file, provenance and checksum validation. Missing data, avatar and sticker versions are archived locally and uploaded to the mode-0700 inbox; the root runner safely extracts and atomically installs them without changing legacy `current` symlinks. The origin key is uploaded to one fixed release-SHA/key-SHA coordinate in that same private inbox and is always removed by the installer or local cleanup. It then stages only the inactive colour and runs direct health/smoke checks; it does not start Caddy or change traffic. It pins the exact candidate data path and stages its versioned Qdrant collection and Neo4j dataset without moving either legacy serving pointer. After private acceptance, `App/scripts/promote.ps1` asks the runner to perform candidate and post-switch smoke tests before atomically updating the promoted environment and colour marker. Promotion discovers the target snapshot's supported ingress services from a fixed allowlist, gates direct origin on the firewall and certificate checks, and recreates Squid, Caddy and only the ingress services that the target snapshot defines. A switch, smoke or mailer failure restores the already validated previous-colour API and edge snapshot; legacy rollback leaves the orthogonal direct-origin listener running rather than treating an application rollback as a DNS rollback. Failure to restore is a hard error. The previous colour retains its own data and media pins throughout.

The root runner alone can set the internal rollback-mode flag. A rollback to a legacy 0.8.x snapshot is refused until a cookie-free, no-redirect request from the host to `https://snow.xiaob.dev/` receives a Cloudflare Access login redirect (or the root-configured Access 403 policy); an application 2xx is always rejected. Install a root-owned mode-`0600` `/etc/project-snow/access-denied-status` containing only `403` when the Access policy intentionally denies without redirect; absence means only the login redirect is accepted. Only after that proof may the legacy post-switch smoke omit the newer ready/full 404 assertion. Live, configuration, 22-character catalogue and private-API-boundary checks still must pass. Normal promotion and every 0.9.x rollback continue to require the strict public smoke, and deploy users cannot supply or override the compatibility flag.

The first 0.9.0 Compose snapshot keeps one migration-only `outbound` bridge because the 0.8.x API expects to find Squid there. Only `egress-proxy` straddles that bridge and the new `egress-client`/`egress-uplink` split; a 0.9 API is contractually forbidden from joining `outbound`. Runtime switching recreates Squid and Caddy from the target snapshot and recreates each target-defined ingress from a fixed allowlist; recovery first restarts the previous API before restoring its known edge services. Ingress services absent from an application snapshot are not automatically retired, because the externally active DNS/Tunnel route is not encoded in the application colour marker. Once a target passes its gates, the previous API is stopped so the legacy inactive image cannot retain direct routed egress. A later immutable release must remove `x-legacy-outbound-retirement`, the proxy's `outbound` attachment and the network itself, but only after both blue and green manifests are 0.9.x or newer and the retained rollback target is no longer 0.8.x. Do not remove the bridge manually or mutate an existing configuration snapshot.

Private acceptance uses only the internal `app`-network IPv4 address printed by a successful, exact-SHA stage. For example, if the stage reports `172.20.0.14:8000`, open `ssh -p 43556 -N -o ExitOnForwardFailure=yes -L 127.0.0.1:18765:172.20.0.14:8000 deploy@server`, then test through client-local `127.0.0.1:18765`. The address is runtime metadata, not a durable release identifier: discard it whenever the candidate container is recreated and require the root runner to resolve and validate the new target rather than guessing or reusing an old address. API test clients should send `Host: snow.xiaob.dev` and the production Origin header when exercising write endpoints; no development origin is enabled in production. Browser-only local acceptance is limited to flows that do not require a production-host Turnstile challenge; the real-host post-switch smoke covers that boundary.

Store the Neo4j password alone in `secrets/neo4j_password` for the API. Store the Docker-image-compatible `neo4j/<password>` value separately in `secrets/neo4j_auth`; the Neo4j container reads it through `NEO4J_AUTH_FILE`, so the password is not placed in Compose interpolation or process arguments.

Start from `ops/public.env.example`, `ops/images.env.example` and `ops/feedback-mailer.env.example`. The public settings file must remain non-secret and contains no SMTP settings; it is never inherited by the SMTP worker. All database URLs, API cryptographic keys, Turnstile secret, Qdrant key, the admin token and passwords are supplied through `/etc/project-snow/secrets` file mounts. The infrastructure image file contains only public image references and immutable digests. The dedicated mailer settings file contains no password. After Alembic creates its `NOLOGIN` role, deploy verifies PostgreSQL statement/parameter logging is disabled, reads the mailer database password only inside the Postgres container, applies it over psql stdin and confirms the role can log in. The worker cannot select feedback text, context or QQ; it sends only the receipt number and submission time.

The public API uses `HTTPS_PROXY=http://egress-proxy:3128`; Squid permits CONNECT only to the five official model API domains and Cloudflare Turnstile. It has no direct uplink. The internal Caddy receives Tunnel traffic through `edge-client` and mutually authenticated direct-origin traffic through the separate `origin-backend`; neither ingress can reach the application/data networks directly. The two fixed origin bridges and host nftables policy prevent the TLS sidecar from initiating Internet or host traffic while leaving only its same-backend connection to Caddy. The feedback mailer is a separate least-privilege worker: it reads only `/etc/project-snow/feedback-mailer.env`, has a dedicated database role limited to receipt/outbox fields, and receives only its database and SMTP password files. The API has neither SMTP credentials nor an admin token, and notification mail contains only the feedback number and time. These are additional SSRF and secret boundaries on top of fixed adapter URLs and redirect rejection.

Only `/public/v1/health/live` is intentionally public. Ready/full health and administration are loopback/SSH-tunnel only. Caddy and ASGI independently enforce a 64 KiB streaming body limit and read timeouts; writes additionally validate the production Host, Origin and JSON Content-Type. Turnstile acceptance is bound to `snow.xiaob.dev`, the expected action and a short challenge age. Static/catalogue GETs do not create identity state; the 30-day Secure `__Host-snow_anon` cookie is created only on the first state-changing request.

Abuse control combines subject, daily rotating HMAC-IP, Cloudflare edge and process concurrency limits. The global generation budget remains four active requests plus eight queued requests and returns `Retry-After` when full. Input/output safety classification runs locally; user content is never sent to a separate moderation provider. Application, proxy and container logs must not contain message bodies, API keys, cookies, raw IP addresses or signed state. Internal request diagnostics live for at most ten minutes and are joined to feedback only by request ID; public SSE exposes only content, usage, validation disposition, movement/scene state and recovery actions.

## Resource policy

The production Compose file caps API, PostgreSQL, Qdrant, Neo4j, embedding, both Caddy processes and cloudflared. Docker JSON logs rotate at 10 MB with five files. PostgreSQL uses `shared_buffers=1GB`, `effective_cache_size=4GB`, `work_mem=8MB` and `max_connections=50`. Deployment reloads the mounted PostgreSQL configuration with SIGHUP and fails closed unless `log_statement=none`, `log_min_duration_statement=-1`, `log_min_error_statement=panic` and both parameter-length logging settings are zero. Normal failures therefore cannot attach SQL text, message bodies or generated responses to PostgreSQL logs.

## Data publication

`export_publishable_graph.py` quarantines reviewed nodes that lack traceable page evidence or use unsupported node types. `verify_data_license.py` freezes every contributing BWiki page revision before `build_data_release.py` packages the derived documents, 512-dimensional vectors, FTS5 database, publishable graph, persona profiles, public attribution index, modification record and license metadata in the exact read-only directory layout consumed by the public API. Raw Wiki pages and images are not copied into the application image or Git history. The loader defaults to stage-only: it creates or verifies `versioned_collection_name(base, data_version)` in Qdrant and `dataset_version=data_version` in Neo4j without changing the shared alias or `SnowDatasetPointer`. Each 0.9 API queries those exact version identifiers. Only the explicit manual command `ops/promote-data.sh <version> --activate` may run the loader's `--activate` path and update legacy pointers; the command refuses a version not pinned to the active colour. Without `--activate`, `promote-data.sh` only verifies and updates compatibility symlinks.

Before a data build, refuse work when disk usage is at least 70% or free space is below 12 GiB. Run builders with a maximum of eight CPUs and 8 GiB of memory. A failed build never changes the `current` symlink or Qdrant/Neo4j active version.

## Backups and recovery

Use restic to an R2 bucket for daily PostgreSQL logical dumps and release manifests. Qdrant snapshots are created when the data version changes; Neo4j is rebuilt from the checked graph import package. Run cleanup immediately after restoring PostgreSQL so feedback older than 30 days is hard-deleted. Private backup retention is seven days; current and previous stable data releases remain available.
