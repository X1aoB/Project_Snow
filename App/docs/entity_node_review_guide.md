# 缺失实体节点审批指南

当关系候选的原文可信、但图谱中没有目标节点时，例如“晴 `VISITS_LOCATION` 汉诺塔”，不要编造节点 ID，也不要因此驳回关系。先通过本流程创建可追溯的地点或事件节点。

## 当前支持范围

系统仅自动发现关系类型能够唯一决定节点类型的端点：

- `VISITS_LOCATION` 的客体 → `location`；
- `PARTICIPATES_IN_EVENT` 的客体 → `event`。

角色、NPC、物品、武器和别名可能对应多个节点类型，仍保持人工映射，避免把称谓、页面名或同名实体误建为正式节点。

## 生成候选

在 `App` 目录运行：

```powershell
python -m pipelines.build_entity_node_candidates --dry-run
python -m pipelines.build_entity_node_candidates
```

候选仅在同时满足以下条件时出现：关系仍待审核、主体有唯一既有演员节点、客体在候选引文和原始文档中逐字出现、且同类型实体节点尚不存在。运行不会创建图节点，也不会改变任何关系候选状态。

## 网页审批步骤

1. 启动 API 与本地预览，访问 `http://127.0.0.1:8080/workspace/`。
2. 在“缺失实体节点审批”中核对实体名称、节点类型、关系端点示例和完整来源片段。
3. 只有在名称与类型都正确时点击“批准并创建节点”。
4. 系统生成稳定的 `location:review_*` 或 `event:review_*` ID，并保留审批人、备注、证据页和关联关系候选。
5. 回到“叙事关系人工审核”，刷新页面；新节点会出现在客体节点 ID 建议中。仍需逐条核对并批准具体关系。

批准节点绝不等于批准关系；批准关系也绝不等于角色本体设定。来自邮件、随机事件、活动、生日或时装的关系会携带 `situational` 或 `costume_specific` 语境，后续检索不能把它们当作无条件的稳定人格事实。

## 不应批准的情况

- 客体只是代词、章节标题、邮件标题或抽取模型概括；
- 原文没有逐字出现该地点/事件名称；
- 已存在同类型、同名节点；
- 你只能依靠游戏常识、图片或未提供的上下文确认实体；
- 该实体实为角色、物品或别名，当前类型无法唯一判断。

这些情况保留在关系审核队列或驳回节点候选即可；源文档不会丢失，后续可在建立别名/实体规范化规则后再处理。
